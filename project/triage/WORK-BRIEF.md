# Writing Work Briefs

A work brief is a structured comment that captures confirmed scope for an issue. It is a durable work contract, not an assignment or a claim that work will begin. The original issue body and discussion remain context; the brief records the agreed behavior and boundaries.

## Principles

### Durability over precision

An issue may remain planned while the codebase changes. Describe contracts and behavior so the brief remains useful when files move or internals are refactored.

- Describe interfaces, types, and behavioral contracts where they are stable.
- Name relevant types, signatures, or configuration shapes when useful.
- Do not reference file paths or line numbers that will go stale.
- Do not assume the current implementation structure will remain unchanged.

### Behavioral, not procedural

Describe what the system should do, not an implementation recipe. A future contributor can explore the current codebase and choose the implementation that satisfies the confirmed contract.

- Good: "The `SkillConfig` type accepts an optional `schedule` field of type `CronExpression`."
- Bad: "Open src/types/skill.ts and add a schedule field on line 42."

### Complete acceptance criteria

Each criterion must be concrete, testable, and independently verifiable. State scope boundaries to prevent accidental expansion into adjacent work.

## Template

```markdown
> *This was generated by AI during triage.*

## Work Brief

**Category:** bug / enhancement
**Summary:** one-line description of the confirmed work

**Current behavior:**
Describe the status quo or broken behavior.

**Desired behavior:**
Describe the observable outcome, including relevant edge cases and errors.

**Key interfaces:**
- `TypeName` - what must remain true or change, and why
- `functionName()` result - current versus desired contract
- Configuration shape - relevant supported options

**Acceptance criteria:**
- [ ] Specific, testable criterion 1
- [ ] Specific, testable criterion 2
- [ ] Specific, testable criterion 3

**Out of scope:**
- Adjacent behavior that must not change
- Related feature tracked separately
```

## Check Before Posting

- The brief reflects a confirmed decision and evidence, not a guess.
- Acceptance criteria verify behavior rather than internal steps.
- Scope boundaries are explicit.
- No file paths, line numbers, or ownership claims are used.
